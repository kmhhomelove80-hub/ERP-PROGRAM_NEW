# SUNIL ERP 통합 업데이트 — 2026년 11월 4일용

생산계획조회, 대메뉴별 직원 권한, 이동 대기 알림, 오른쪽 업무 조회 영역, 기존 메뉴·검색·피킹 개선을 포함합니다. **회사 ERP 서버에서 기존 Windows 계정으로 실행하는 업데이트**이며 새 설치·DB 재이관용이 아닙니다.

이 배포본에는 EXE가 없습니다. 기존 Python으로 공개된 업데이트 코드를 실행합니다. 백신 허용·제외 설정, 실행 정책 변경, 자동 관리자 권한 전환을 하지 않습니다. Windows 보안이 이 파일도 차단하면 진행하지 말고 화면을 전달해 주세요. 이전에 보류한 EXE는 사용하지 않습니다.

이번 v2는 이전 배포에서 갱신되지 않았던 매뉴얼 원고 MD를 교체 대상에서 제외합니다. 기존 서버 원고는 보존하며, 화면·PDF 매뉴얼과 프로그램 기능은 검증된 통합본과 같습니다. v1 검사에서 중단된 경우 v2로 새로 사전 점검합니다.

## 1. 준비

1. 회사 ERP 서버에 평소 사용하던 **기존 Windows 계정(비밀키를 만든 계정)**으로 로그인합니다. 기존 ERP 접속이 정상인지 확인합니다.
2. 새 ZIP을 다운로드합니다. 파일 이름은 `SUNIL-ERP-20261104-integrated-v2.zip`입니다.
3. 압축을 풀어 다음 위치에 둡니다. 폴더 안에 `Update-Erp.py`, `manifest.json`, `app` 폴더가 바로 보여야 합니다.

   `C:\SUNIL\updates\SUNIL-ERP-20261104-integrated-v2`

   압축 해제 결과 같은 이름의 폴더가 두 번 겹쳐 있으면 실제 파일이 들어 있는 안쪽 폴더를 위 위치로 옮깁니다. `app` 폴더를 기존 ERP에 직접 덮어쓰지 마세요.
4. 다운로드한 ZIP과 압축 해제 폴더를 사용 중인 백신으로 검사합니다. 차단·경고가 나오면 허용하지 말고 중단합니다.
5. 시작 메뉴에서 **Windows PowerShell**을 검색하고 **관리자 권한으로 실행**합니다. 같은 Windows 계정으로 승인합니다. 다른 관리자 계정의 암호를 요구하면 취소하고 알려 주세요.

아래 명령은 하나씩 실행합니다. 앞선 대화에서 사용한 `$Config` 같은 변수나 PowerShell 스크립트 로딩은 필요하지 않습니다.

## 2. 사전 점검 — 먼저 이 명령만 실행

```powershell
& 'C:\SUNIL\ERP\.venv\Scripts\python.exe' 'C:\SUNIL\updates\SUNIL-ERP-20261104-integrated-v2\Update-Erp.py' check
```

**‘사전 점검 완료’**가 나와야 다음 단계로 갑니다. 이 단계는 서버를 중지하거나 프로그램을 교체하거나 DB 구조를 변경하지 않습니다. 점검 로그와 중복 실행 방지 파일은 만듭니다.

오류·차단·예상과 다른 경로가 나오면 **다음 명령을 실행하지 말고** 화면을 전달해 주세요. ‘이미 같은 통합 배포본이 적용되어 있습니다’가 나오면 다시 업데이트할 필요가 없습니다.

## 3. 업데이트 실행

직원들에게 잠시 **입고·출고·예약·이동 처리·생산계획 업로드·권한 변경을 멈춰 달라**고 알립니다. 다른 프로그램에서 같은 DB에 쓰는 작업도 중단합니다. 그다음 아래 한 명령을 실행합니다.

```powershell
& 'C:\SUNIL\ERP\.venv\Scripts\python.exe' 'C:\SUNIL\updates\SUNIL-ERP-20261104-integrated-v2\Update-Erp.py' apply --work-paused
```

도구는 아래 순서를 자동 처리합니다.

1. 기존 예약 작업 상태를 기록하고 정시 백업과 충돌하지 않도록 준비합니다.
2. **DB 백업과 SHA256 검증 후** ERP를 중지합니다. PostgreSQL과 Caddy는 유지합니다.
3. 중지 시점의 최신 DB 백업·비교값과 기존 코드 복구본을 만듭니다.
4. 배포 파일 체크섬을 확인하고 프로그램 파일을 교체합니다. 서버의 별도 수정 파일은 자동으로 덮어쓰지 않습니다.
5. 예정된 **0012 생산계획 / 0013 대메뉴 권한** 외의 변경이 없는지 검사한 뒤 필요한 마이그레이션만 적용합니다. 이미 적용된 것은 다시 만들지 않습니다.
6. 정적 파일 수집, 기존 업무 데이터·계정·설정 보존 검사, ERP 재시작, 로그인 화면·정적 파일·로그인 후 읽기 화면 검사를 진행합니다.
7. 업데이트 후 DB 백업을 검증하고 기존 정시 백업 설정을 복구합니다.

완료될 때까지 PowerShell 창을 닫거나 컴퓨터를 끄지 마세요. 백업 용량에 따라 시간이 걸리며 진행 메시지와 로그를 남깁니다. **‘업데이트와 백업 검증 완료’**를 확인합니다.

## 4. 화면 확인 후 업무 재개

1. 기존 ERP 주소에 접속하고 PC에서 **Ctrl+F5**로 새로고침합니다. 휴대폰도 새로고침합니다.
2. 상단 오른쪽 별도 영역의 **생산계획조회**를 확인합니다.
3. 생산계획조회가 모두 가능한 계정에서 **엑셀 열기 · 열 연결 설정**으로 파일을 읽고, 시트·헤더 행·데이터 시작 행·13개 열 연결을 확인한 뒤 공유 자료로 적용합니다. 동명 헤더는 직접 열을 선택합니다.
4. 조회 계정에서는 검색·정렬·선택 행의 부품 표시가 되고 업로드 버튼은 없는지 확인합니다.
5. **관리 → 직원 계정 → 직원 선택**에서 입고 관리·출고 관리·생산계획조회·재고 관리·관리의 다섯 선택란을 확인합니다. 기존 전체 권한 직원은 모두 가능, 기존 작업자는 조회만 가능으로 보존됩니다. 필요한 직원에게만 대메뉴별로 권한을 부여합니다. 새 직원의 기본값은 모두 조회만 가능입니다.
6. 현장 직원의 이동 요청이 대기 중이면 **재고 관리가 모두 가능한 직원**에게 상단 알림과 건수가 표시됩니다. 클릭하면 대기 목록이 열리며 처리 완료·거부 후 건수에서 제외됩니다. 화면이 보이는 동안 60초마다, 다시 화면으로 돌아왔을 때 갱신합니다.
7. 재고 조회의 제품명·사양 동시 검색과 메뉴 겹침 방지, **운영 점검의 원장·예약 합계 일치**를 확인합니다. 확인을 위해 실제 출고나 재고 이동을 임의로 실행하지 않습니다.
8. 완료 메시지의 백업 위치를 기록합니다. 다음 정시 로컬 백업 성공도 확인합니다. 확인 후 직원들에게 업무 재개를 알립니다.

## 중단·실패·정전이 발생하면

- **‘기존 코드와 예약 작업으로 복구했습니다’**: 기존 ERP 접속을 확인하고 오류 화면과 로그를 전달해 주세요. 기존 코드로 돌렸더라도 추가된 DB 테이블은 보존합니다. DB를 과거 백업으로 덮어쓰지 않습니다.
- **‘자동 복구를 마치지 못했습니다’**: 반복해서 apply를 실행하거나 DB를 복원하지 마세요. 업무 처리를 멈춘 상태에서 로그를 전달해 주세요.
- 창이 강제로 닫혔거나 미완료 기록이 있으면 같은 계정·같은 배포 폴더에서 다음 명령으로 **코드·예약 작업만 복구**합니다.

```powershell
& 'C:\SUNIL\ERP\.venv\Scripts\python.exe' 'C:\SUNIL\updates\SUNIL-ERP-20261104-integrated-v2\Update-Erp.py' recover
```

- 복구 후 다시 check부터 시작합니다. 복구 오류가 나면 더 진행하지 않습니다.
- **마지막 백업 경고**만 나오면 업데이트와 웹 검사는 완료된 상태입니다. 중지 시점의 검증된 백업은 남아 있습니다. 업데이트를 반복하지 말고 로그를 전달해 주세요.

## 보존 및 기록

기존 DB·계정·비밀번호·로컬 설정·DPAPI 비밀키·실제 Caddy 설정·현재 내부 HTTP 및 DEBUG=1을 보존합니다. 기존 `Run-Erp.ps1`·`Common.ps1`과 Caddy/예약 작업 정의를 덮어쓰지 않으며 공유기·외부 접속 설정을 변경하지 않습니다. DB 초기화·재이관·자동 DB 복원은 없습니다. 추가 마이그레이션은 생산계획·직원별 메뉴 권한용 새 테이블만 만듭니다.

백업은 기존 설정의 로컬 백업 폴더를 사용합니다. 실제 경로는 실행 중 출력합니다. 적용 기록·기존 코드 복구본·검사 stdout/stderr는 기존 DataRoot 아래 `standard-update-runs`에, 사전 점검 로그는 배포 폴더의 `logs`에 남깁니다. 비밀키·DB 암호를 로그나 명령행에 출력하지 않습니다. DB 백업이나 비밀키 파일은 외부에 공유하지 마세요.

`VALIDATION.json`에는 공개 검증 실행과 검증 코드 기준을, `manifest.json`에는 배포 파일 체크섬을 기록합니다. 배포 ZIP의 SHA256도 다운로드 페이지에서 제공합니다. 체크섬은 손상 확인용이며 백신의 안전 판정을 대신하지 않습니다.
