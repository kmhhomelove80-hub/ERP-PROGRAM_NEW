# SUNIL ERP 2026-11-03 업데이트 안내

기준: `d425d71`. 운영 Windows 11 / Python 3.12 / PostgreSQL 18 / 앱 `C:\SUNIL\ERP` / 설정 `C:\ProgramData\SUNIL\runtime.local.json`.

이번 배포는 코드 업데이트입니다. 새 DB 마이그레이션과 의존성 변경은 없습니다. 기존 DB·계정·입고/피킹/예약·이력을 보존합니다. 운영 DB 초기화·재이관·복원·계정 재생성은 하지 않습니다. 현재 HTTP와 `ERP_DEBUG=1`을 유지합니다. HTTPS·NAS·고정 IP 설정 작업은 이번 업데이트 범위에 포함하지 않습니다.

## 변경 내용과 사용 방법

- 자동 배정: 다른 예약을 제외한 위치별 가용량 합산 → 한 위치 전량 일치 → 두 위치 전량 일치 → 한 위치 충족 시 최소 잔량 → 여러 위치의 최소 위치 수와 최소 가용량 합계. 최초 예약은 입고 완료/예정 동등. 예정 재고 출고는 도착 확인 후 가능. 추가 피킹은 기존처럼 입고 완료된 미배정 잔여 수요만 추가합니다.
- 예약 전: 미리보기 하단 ‘예약 전 위치·수량 수동 조정’의 실제 재고 ID·수량을 입력 → 수동 미리보기 → 예약 확정. 품목별 배정 가능 합계를 유지합니다.
- 예약 후: 피킹 상세 또는 예약/출고의 ‘위치·수량 변경’ → 실제 재고 ID·수량, 사유, 확인 → 저장. 예약을 원자적으로 재분배하고 주문·프로젝트·기존 SEQ·총수량을 유지합니다. 출고·취소 완료 행은 변경 불가. 대체품 예약은 기존 빌림 연결 보존을 위해 한 재고로만 변경할 수 있습니다.
- 오래된 예약/출고 화면: 위치·수량 변경 후 이전 화면에서 출고·취소를 제출하면 다시 조회하도록 차단합니다. 서명된 표시 당시 배정과 실행 시 배정을 같은 트랜잭션 안에서 비교합니다.
- 변경 기록: 관리 → 작업 이력 → 예약 위치 변경. 이전 위치·수량과 새 위치별 수량, 사유, 처리자·시각을 확인합니다.
- 정리 리스트: 확인된 사용자 기준대로 입고 완료 실재고만 사용. 같은 품목·동일 위치 행을 합산해 3개 이하인지 판정. 예약 있는 위치는 출발·도착 후보 모두 제외. 적격 위치 중 보유량 최대 위치가 기본 도착이며 동률은 위치명·재고 ID 순. 비울 위치 수가 많은 품목 우선. 도착 공간·보관 조건은 작업자 확인. 필요 시 조회·인쇄하고 기존 이동 요청/관리자 실행 절차 사용. 자동 정기 출력과 출력 시 재고 변경은 없음.
- 메뉴: 재고 조회 / 입고 관리 / 출고 관리 / 재고 관리 / 관리. 휴대폰에서도 그룹 메뉴를 열 수 있습니다. 직원 계정과 실행 버튼은 관리자 전용입니다.
- 작업자—조회·이동 요청: 기존 일반 계정 그대로 이동 요청 등록·전체 처리 상태 조회 가능. 요청 등록 자체는 재고를 바꾸지 않습니다. 실제 이동은 관리자 승인·실행 시 가용량 재검사. 입고·예약·출고·ERP 수정 등 다른 쓰기 권한은 확대하지 않습니다.
- 첨부 ZIP 반영: Binary Eye 정규화 미들웨어, 재고 화면 개발 배너 제거, 운영 점검의 개발 환경 문구 제거를 보존했습니다. 재고/운영 화면의 나머지 기존 기능은 유지합니다.

## 동률·계산 비용

위치명은 Python Unicode 코드포인트 오름차순, 동일 위치의 재고 행은 ID 오름차순입니다. 입고 상태는 선호 기준으로 사용하지 않습니다. 선택된 위치의 재고 행을 이 순서로 채우며 마지막 행은 필요한 만큼만 예약합니다. 위치명은 원장 문자열 그대로 비교하며 대소문자나 공백이 다른 위치를 임의로 합치지 않습니다.

단일 일치·두 위치 정확 합은 선형 탐색, 한 위치 최소 잔량도 선형 탐색입니다. 여러 위치는 큰 가용량 순 누적으로 최소 위치 수를 확정하고, 해당 위치 수에 대한 희소 동적 계획법으로 최소 초과합을 정확히 찾습니다. 같은 합계는 위치 순서로 결정합니다. 부분합 문제이므로 일반적인 다항시간 보장은 없습니다.

복잡한 조합 단계에서만 품목당 200위치, 50,000개 중간 상태, 전체 피킹 계획 2,000,000개 상태 전이로 계산을 제한합니다. 단일/두 위치 정확 일치 등 빠른 단계는 200위치를 넘어서도 동작합니다. 한도 초과 시 임의 근사안으로 예약하지 않고 명시적으로 중단해 수동 배정 미리보기로 진행하게 합니다. 재고는 바뀌지 않습니다. 동시 처리에서는 기존 PostgreSQL 창고 단위 advisory lock과 트랜잭션·행 잠금을 유지합니다.

개발 환경 측정: 10,000위치 단일 일치 약 0.0003초, 두 위치 일치 약 0.0012초, 200위치 반복 수량 조합 약 0.001초, 큰 수량의 복잡한 40위치 입력은 약 0.031초에 계산 한도 안내. DB 조회·화면 출력은 제외한 예시이며 서버 성능 보장은 아닙니다.

## Binary Eye

공식 [README Deep Links](https://github.com/markusfisch/BinaryEye#deep-links)와 [Android Manifest](https://github.com/markusfisch/BinaryEye/blob/master/app/src/main/AndroidManifest.xml)에서 `binaryeye://scan` 및 `ret` URI 템플릿을 확인했습니다. 스캔 아이콘은 Android에서 공식 URI를 실행하며 반환 주소는 현재 ERP 접속 origin의 `/?scan=1&content={RESULT}`입니다. 외부 앱을 열 수 없을 때에도 ERP의 안내가 남도록 별도 브라우저 컨텍스트에서 실행합니다. 미설치·구버전·브라우저 제한은 안내의 실행/설치 링크 또는 앱 직접 실행으로 대응합니다. iOS·Windows 등은 직접 검색/키보드형 스캐너를 안내합니다.

기존 확인된 앱 설정도 그대로 사용 가능합니다.

1. 전달 스캔 켜기.
2. 요청 유형: 외부 브라우저에서 열기.
3. 전달 URL: `http://192.168.0.252:8080/?scan=1`.

루트 GET, `scan=1`, 빈 `q`, 공백 제거 후 1~100자 `content`만 `/?scan=1&q=...`로 인코딩해 리다이렉트합니다. 제어문자는 거부합니다. 기존 `q`는 덮어쓰지 않고 다른 경로나 POST는 변환하지 않습니다. 로그인이 없으면 기존 로그인 절차를 따릅니다. 입력값은 코드 검색에만 사용하며 외부 주소로 리다이렉트하지 않습니다.

실제 앱 설치 여부·버전·브라우저 정책은 이 개발 환경에서 확인할 수 없습니다. 서버 파일 업데이트 후 실제 Android에서 앱 열림 → 라벨 스캔 → 회사 Wi-Fi의 ERP 복귀 → 기존 품목의 위치·수량 표시를 확인하세요. 기존 전달 스캔도 켜져 있으므로 앱 버전에 따라 반환 탭이 중복될 수 있습니다. 이 경우 직원이 사용하는 실제 앱 버전과 브라우저를 기록해 주세요. 중복 GET은 조회이며 재고를 변경하지 않습니다.

## Waitress와 PowerShell

`Run-Erp.ps1`은 설정 오류에 대한 `Stop` 정책을 유지하고, `Start-Process`의 stdout/stderr 파일 리다이렉션을 사용합니다. 따라서 Windows PowerShell 5.1이 정상 Waitress stderr 안내를 `NativeCommandError`로 처리하는 경로를 피합니다. 자식 Python의 실제 종료 코드를 예약 작업에 그대로 반환합니다. 설정/실행 시작 실패는 코드 1입니다.

로그는 `DataRoot\logs\server-날짜-시각-PID.log`(시작/종료 코드), `.stdout.log`, `.stderr.log`로 실행마다 보존합니다. 정상 Serving 안내는 stderr 로그에 있어도 실패가 아닙니다. 비정상 종료는 stderr와 lifecycle 로그를 함께 확인합니다. 예약 작업을 강제 중지한 경우에는 프로세스가 종료 기록을 쓰지 못할 수 있으므로 작업 스케줄러 기록도 확인합니다.

PowerShell 7.4.6 Linux에서 문법 및 정상 stderr/종료 코드 0, 실제 비정상 종료 7, 설정 실패 1, 로그 분리를 검증했습니다. Windows 5.1·DPAPI·예약 작업의 실제 실행은 현장 재시작 확인 대상입니다.
